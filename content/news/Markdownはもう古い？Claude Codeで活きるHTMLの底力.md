## 記事の概要

Claude がより複雑な仕様書・計画・レポートを書けるようになった現在、
Claude Code で成果物を作る際は **HTMLの方がいいですよ**、といった内容の記事。

というのも、人間が実際に読み、レビューし、共有できる形式としては
MarkdownよりもHTMLの方が優れている場面がいくつかあるとのこと。

## メリット

**1. 情報密度が圧倒的に高い**

MarkdownだとASCII図やUnicode文字での色表現といった
非効率な代替手段に頼りがちになる一方で、
HTMLであれば、表、CSSによるデザイン、SVG イラスト、コードスニペット、
JavaScriptによるインタラクション、ワークフロー図、画像など、ほぼあらゆる情報を表現できる。

**2. 視覚的に読みやすい**

100 行を超えるMarkdownは自分でも他人でも読む気にならないが、
HTMLならタブ・図・リンクで構造化でき、モバイル対応も可能なので、
実際に読んでもらえる確率が大幅に上がる。

**3. 共有しやすい**

Markdownはブラウザでネイティブに表示されず添付が必要だが、
HTMLはアップロードしてリンクを共有するだけで済む。

**4. 双方向のインタラクションが可能**

スライダーやノブで設定を試したり、変更内容をプロンプトとしてコピーしてClaude Codeに戻す
といった「使い捨ての編集環境」を作れる。

**5. 豊富なコンテキストを取り込める**

Claude Codeはファイルシステム、MCP（Slack や Linear など）、ブラウザ、Git 履歴から
情報を集約してHTMLに落とし込める。

**6. ループに留まれる**

Claudeの判断にきちんと関与し続けられるため、丸投げにならない。

> [!info] ※これが筆者にとって最大の理由らしい。

## 実践方法

### 始め方

「HTMLファイルを作って」「HTMLアーティファクトを作って」と指示する。
重要なのは **そのアーティファクトに何をさせたいか、どう使いたいか** を明確にすること。

> [!tip] 繰り返し使うパターンが見えてきたら、スキルとして整備するのが良い。

### 主なユースケースとプロンプト例

#### ① 仕様・計画・アイデア検討

ひとつの計画書ではなく、検討案・モックアップ・実装計画など複数のHTMLファイル群を作る。
検証エージェントにもこれらを読ませると広いコンテキストで作業してくれる。

```
例：
オンボーディング画面の方向性を 6 通り作って、
グリッド表示で比較できるHTMLにして。各案のトレードオフも注釈して。
```

#### ② コードレビューと理解

差分、注釈、フローチャート、モジュール構造を視覚的にレンダリングできる。
PR の作成・レビュー・コード理解に有効。

```
例：
この PR をレビューしたい。
ストリーミング周りに不慣れなのでそこを重点的に、差分にインライン注釈をつけ、
所見を重要度で色分けしたHTMLを作って。
```

#### ③ デザインとプロトタイプ

最終出力がReactやSwiftであっても、まずHTMLでデザインを作ると効率的。
スライダーやノブで動きを調整する用途にも向く。

```
例：
クリックでアニメーションし紫色に変わるチェックアウトボタンを、
複数のスライダーで調整できるHTMLにして。良かったパラメータをコピーするボタンも。
```

#### ④ レポート・リサーチ・学習

複数のデータソースを横断して、解説書・スライド・インタラクティブな説明資料を生成できる。
図解にはSVGを使わせると良い。

```
例：
うちのレートリミッターの動作を理解したい。
コードを読んで、トークンバケットの図、主要コードへの注釈、
落とし穴セクションを含む解説HTMLを作って。
```

#### ⑤ カスタム編集インターフェース

特定のデータを編集するためだけの「使い捨てエディタ」を作ってもらう。
**コツは必ず「JSONとしてコピー」「プロンプトとしてコピー」などのエクスポート機能で締めくくること**。
これによりUI上の作業結果をClaude Codeに貼り戻せる。

```
例：
30件のLinearチケットを
Now / Next / Later / Cut の4列にドラッグで振り分けられるHTMLを作って。
最終結果を理由付きのMarkdownでコピーできるボタンも。
```

## 運用上のTips

- **トークン効率より人間が読む確率を優先する**
  Markdownより消費は増えるが、
  大きなコンテキストウィンドウがあるので問題になりにくく、得られる成果の質の方が重要。
- **計画は分割する**
  単一の計画書ではなく、実装計画・UI 検討・デザイン一覧など、
  目的別に複数のHTMLファイルへ分割して保管しておくと、後から参照や検証にも使える。

### 主要な原因の推察

#### 総合解釈

要因を整理すると、ざっくりこんな寄与度ではないかと推察します。

1. **Markdown テーブル記法の冗長性**（最大の要因）
2. **キャッシュヒット率の差**（HTML 有利）
3. **情報収集戦略の違い**（HTML 有利）
4. **箇条書きマーカーの累積**
5. **サブエージェント呼び出しの差**

#### 詳細

##### 1. Markdown のテーブル記法が想像以上に冗長

両プロンプトとも「各発表について『概要/主な機能/ターゲットユーザー/既存サービスとの違い』を整理」
と指示していました。Claude はこれを表現するのに、ほぼ確実に **表形式** を使ったはずです。

Markdown のテーブルはこんな構造になります:

```
| 項目 | 内容 |
|------|------|
| 概要 | XXX |
| 主な機能 | YYY |
```

これに対して HTML は:

```
<table>
<tr><td>概要</td><td>XXX</td></tr>
<tr><td>主な機能</td><td>YYY</td></tr>
</table>
```

一見 HTML の方が冗長に見えますが、
**実は Claude 系のトークナイザーでは `<td>` `<tr>` などの HTML タグは「よく出現する単位」として効率的にトークン化される** 傾向があります。
一方 Markdown のパイプ `|` とハイフン区切り `|------|` は、テーブルが大きくなるほどパディングとセパレーター行のトークンが累積していきます。

**Output トークン差 4.3k のうち、おそらく半分以上はテーブル記法のオーバーヘッドではないか** と推測します。

##### 2. Markdown は箇条書きの「マーカー」が繰り返される

Markdown は箇条書きで `-` や `*` を各行の先頭に置きます。
長いリストになるほどこのマーカー分のトークンが積み上がります。
HTML の `<ul><li>...</li><li>...</li></ul>` は、開始タグと終了タグが各要素を囲む形なので、
構造としてはむしろシンプルです。

特に今回のような「発表内容を多数列挙する」タスクでは、
リストの数が非常に多くなったはずで、この差がじわじわ効いてきます。

##### 3. Web 検索戦略の違いがコストに反映された

検索回数を見ると明確な対照があります:

- **Markdown 版**：3 回検索 / Haiku Input 98.0k
- **HTML 版**：11 回検索 / Haiku Input 27.6k

Markdown 版は「少ない検索で大量の結果を一度に取り込む」戦略、
HTML 版は「多数の小さい検索でキャッシュを活用する」戦略になっています。
これは Claude が出力形式を意識して **情報収集の粒度を変えた** 可能性があります。

HTML 版では「リンクとして機能させる」という指示があったため、
各セクション用の正確な URL を確保するため **小刻みに検索した** のかもしれません。
結果として 1 回あたりの取り込み量が少なくなり、キャッシュヒット率が上がって総コストが下がった、
と考えられます。

##### 4. キャッシュヒット率の差

Opus 4-6 の Cache Read を比較すると:

- Markdown 版：226.1k
- HTML 版：447.6k（**約 2 倍**）

HTML 版の方が圧倒的にキャッシュを再利用できています。
Cache Read のコストは通常の Input の 10 分の 1 程度なので、ここで大きく節約できたのが効いたはずです。

なぜ HTML 版でキャッシュが効きやすかったのか。
これは推測ですが、HTML 版は段階的に構造を組み立てていく
`<head>` を書く、`<style>` を書く、本文を埋める…プロセスで、
**過去のコンテキストを参照するパターンが多発した** ためにキャッシュヒットが増えた可能性があります。

##### 5. 出力の冗長度が違った可能性

これは推測の域を出ませんが、Markdown は **「自由度が高すぎる」フォーマット** でもあります。
見出しレベル、リストの深さ、表の有無、強調の使い方など、
Claude が「より丁寧に書こう」と判断する余地が大きい。

一方 HTML は構造化の枠が比較的明確で、
「このセクションには `<section>` を使う」「リストは `<ul>` で囲む」といった **「型」がはっきりしている** 分、
Claude が冗長な装飾を加えにくかった可能性があります。

逆説的ですが、**「自由度が高いから冗長になる」** という現象が Markdown 側で起きたのではないでしょうか。

##### 6. サブエージェントの呼び出しパターンの差

Markdown 版では `general-purpose` サブエージェントが呼び出されています（HTML 版では未呼び出し）。

これは推測ですが、テーブル整形や複数発表の比較整理で、汎用エージェントを使った可能性があります。
サブエージェントはそれぞれ独立したリクエストを発行するので、その分のトークンも累積します。

```
- 末尾に「開発者への影響」「個人ユーザーへの影響」の 2 セクション

【制約】
- 出典 URL を各セクションに明記（クリック可能なリンクとして）
- 推測ではなく検索結果に基づく事実のみを記載
- 不確実な情報には「※未確認」のバッジを付ける
```
